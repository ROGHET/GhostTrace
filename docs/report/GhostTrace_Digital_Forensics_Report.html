Abstract

GhostTrace is an academic digital forensics investigation conducted within the TryHackMe Autopsy forensics laboratory environment. The investigation examines a pre-prepared Windows NTFS disk image representing a system on which an insider data exfiltration incident is suspected. The primary examination tool is Autopsy Digital Forensics Platform (version 4.21), supplemented by custom Python scripts for SHA-256 evidence integrity verification, evidence inventory generation, and incident timeline normalization.

The investigation correlates artifacts across five artifact categories: Windows Security and System Event Logs, Chromium browser history, NTFS Master File Table (MFT) metadata, Recycle Bin records, and the Autopsy-generated file-system timeline. The evidence supports a finding that the suspect user account performed a focused, deliberate sequence of actions over a 19-minute session: gaining administrative access, staging sensitive financial data in a compressed archive, transferring the archive to a public file-transfer service (WeTransfer), and then deleting the archive and emptying the Recycle Bin in an apparent anti-forensic cleanup.

Twelve findings are documented in the findings register, nine of which carry high confidence ratings. The investigation demonstrates how multi-source artifact correlation can reconstruct an incident timeline even when the attacker attempts to cover their tracks, while acknowledging the inherent limitations of NTFS timestamp analysis, the absence of network packet capture, and the educational nature of the dataset.

1. Introduction

1.1 Brief Overview of the Project

GhostTrace is a digital forensics mini-project developed as part of Theory Internal Assessment 2 for the Honours Program in Cyber Security and Forensics at K. J. Somaiya School of Engineering, Somaiya Vidyavihar University. The project demonstrates a complete digital forensics investigation workflow — from evidence acquisition and integrity verification through artifact examination and timeline reconstruction — within an authorized educational laboratory environment.

The investigation is conducted using the TryHackMe Autopsy forensics room, which provides a pre-prepared Windows NTFS disk image for examination. Autopsy Digital Forensics Platform serves as the primary examination tool, and custom Python scripts automate key repeatable tasks including SHA-256 hashing, evidence inventory generation, and timeline normalization.

1.2 Background and Motivation

The threat posed by insiders — employees, contractors, or trusted users who misuse their legitimate access to organizational systems — represents one of the most difficult-to-detect categories of cybersecurity incidents. Unlike external attackers, insiders bypass perimeter controls by design. Their activities may leave few immediate indicators, particularly when they use legitimate credentials and native operating system tools.

Digital forensic investigation provides the means to reconstruct what occurred after the fact, drawing on the artifacts that operating systems, applications, and file systems inevitably leave behind. Even when an insider attempts to cover their tracks by deleting files, clearing logs, or using non-attributable transfer services, a thorough forensic examination of a disk image can frequently recover sufficient evidence to establish a coherent sequence of events.

This project is motivated by the recognition that understanding forensic investigation methodology — not just in theory but through hands-on practice — is essential for any cybersecurity professional who may be called upon to investigate, respond to, or help prevent such incidents.

1.3 Digital Forensics Context

Digital forensics is the discipline of recovering, preserving, and analyzing digital evidence in a manner that maintains its integrity and supports accurate, defensible conclusions. The field encompasses forensic examination of storage media, volatile memory, network traffic, and cloud-hosted data. In criminal and civil proceedings, digital evidence is subject to strict chain-of-custody requirements and admissibility standards.

This project follows the NIST SP 800-86 guide to integrating forensic techniques into incident response and applies the four-phase forensic process: collection, examination, analysis, and reporting [NIST 2006]. The investigation is academic in nature and does not claim to satisfy legal chain-of-custody standards; however, the methodology demonstrates principles that apply to real forensic investigations.

The Autopsy Digital Forensics Platform, built on The Sleuth Kit (TSK) open-source library, is one of the most widely used open-source forensic tools globally. It supports examination of NTFS, FAT, exFAT, EXT2/3/4, HFS+, and other file systems, and provides a comprehensive suite of ingest modules for artifact extraction.

1.4 Scope of the Investigation

This investigation is scoped to the following artifact categories, which are supported by the evidence available in the TryHackMe lab disk image:

  • File-system metadata and directory structure (NTFS MFT)
  • File creation, modification, and access timestamps
  • Deleted-file indicators and recoverable Recycle Bin metadata
  • Chromium browser history (URLs, timestamps, visit counts)
  • Windows Security and System Event Logs
  • User activity and evidence of file access
  • Correlation of artifacts to reconstruct an incident sequence

Network packet capture, volatile memory forensics, and email artifact analysis are outside the scope of this investigation due to the absence of corresponding evidence sources in the available dataset.

2. Objectives and Problem Statement

2.1 Problem Statement

Organizations face significant difficulty detecting and investigating insider data exfiltration incidents. When an insider with legitimate access decides to steal sensitive data, they often use standard system tools and public services that generate minimal immediate alerts. The challenge for forensic investigators is to reconstruct the incident from the digital traces left on the suspect system — traces that the attacker may have partially attempted to erase.

The specific question this investigation seeks to answer is: What artifacts on the suspect system indicate unauthorized data access or exfiltration, and what is the reconstructed sequence of events?

2.2 Objectives

  1. Establish a forensically sound examination procedure for the available disk image, including SHA-256 integrity verification and evidence inventory documentation.
  2. Use Autopsy to examine file-system metadata, browser history, Windows event logs, and Recycle Bin records on the disk image.
  3. Identify and document forensic artifacts that indicate file access, data staging, data transfer, and anti-forensic activity.
  4. Correlate the identified artifacts to construct a chronological incident timeline with confidence ratings and documented limitations.
  5. Answer the investigation question directly and distinguish established findings from inferences and unresolvable uncertainties.
  6. Automate key repeatable investigation tasks using Python scripts that are tested, documented, and reproducible.
  7. Produce a comprehensive academic report suitable for assessment and viva.

2.4 Scope and Limitations

In scope: File-system metadata, Windows event logs, browser history, Recycle Bin artifacts, Autopsy timeline, Python-automated analysis.

Out of scope: Network packet capture, volatile memory forensics, email client artifacts, mobile device forensics, cloud service forensics.

Key limitations: The investigation relies on a simulated educational dataset; NTFS access timestamps are subject to OS suppression; upload contents cannot be verified from local artifacts alone; no behavioral baseline is available for the user account.

3.1 Hardware and Software Environment

The primary investigation environment is the TryHackMe web-based lab, which provides a virtual machine accessible via a browser. The disk image within the lab runs on a Windows-based VM. Local development of Python scripts was performed on a Windows 10/11 workstation with Python 3.10+ installed. Autopsy 4.21 was used within the TryHackMe lab environment or on the local workstation after downloading the relevant lab image.

3.2 Evidence Integrity and Preservation

Evidence integrity is maintained through the following measures:

  1. SHA-256 hashing: The disk image SHA-256 hash is computed before any examination using either certutil -hashfile <image> SHA256 (Windows) or the project's hash_evidence.py script. The hash is recorded in evidence/hash_manifest.txt.
  2. Read-only access: Autopsy opens disk images in read-only mode by default. All Python scripts use read-only file access; no script modifies original evidence.
  3. Evidence inventory: All evidence files are catalogued in evidence/evidence_inventory.csv with metadata including filename, size, extension, and acquisition timestamp.
  4. Working copies: Where local analysis is performed, copies of exported artifacts (CSV exports from Autopsy) are used; the original image is not duplicated locally.

3.3 Tool Selection Rationale

Autopsy was selected as the primary tool because it provides an integrated GUI for NTFS forensic examination, supports automated artifact extraction via ingest modules, generates chronological timelines, and is widely used in both academic and professional digital forensics practice. The open-source nature of Autopsy and TSK also means the methodology is independently reproducible.

TryHackMe was selected as the lab platform because it provides a legally authorized, pre-prepared forensic image specifically designed for Autopsy-based investigation. This eliminates the need for the team to acquire a separate forensic image and ensures the investigation targets appropriate, purposely-designed forensic artifacts.

3.4 Legal and Ethical Considerations

This investigation is conducted entirely within an authorized educational platform (TryHackMe). All evidence is simulated training data. No real individual, organization, or production system was accessed, targeted, or affected. The project operates within the following ethical boundaries:

  • Only the TryHackMe-provided lab image is examined — no unauthorized data access.
  • No real personal data, credentials, or sensitive organizational information is included in any deliverable.
  • The investigation findings are presented as educational conclusions from simulated data.
  • Platform terms of service (TryHackMe) are respected; lab flags and answers are not published publicly.
  • The report explicitly distinguishes the educational simulation from real criminal investigation.

4. Methodology and Implementation

4.1 Case Background and Evidence Sources

The investigation is framed around a simulated insider threat incident. The suspect system is a Windows workstation belonging to a user 'John'. The disk image captures the file system state following the suspected incident. The investigation question is whether forensic artifacts on this system can establish that an insider data exfiltration event occurred and, if so, reconstruct its sequence.

Evidence sources examined are listed in the evidence inventory (Section 3.2 and evidence/evidence_inventory.csv). The principal sources are the disk image file system (NTFS MFT), Windows Security and System event logs, Chromium browser history database, and the Recycle Bin metadata directory.

4.2 Phase A — Evidence Acquisition and Integrity Verification

The disk image was obtained from the TryHackMe Autopsy forensics lab environment. The acquisition procedure is as follows:

  1. Log into TryHackMe and deploy the Autopsy lab machine.
  2. Identify the disk image filename, path, and size as shown in the lab.
  3. Calculate the SHA-256 hash of the disk image before opening it in Autopsy:
# Windows (in TryHackMe lab terminal or PowerShell)
certutil -hashfile "C:\path\to\disk_image.dd" SHA256

# Or using the project script
python scripts/hash_evidence.py --path evidence/ --output evidence/hash_manifest
  1. Record the hash in evidence/hash_manifest.txt and evidence/hash_manifest.json.
  2. Confirm the evidence inventory is complete (evidence/evidence_inventory.csv).

Note on chain of custody: This investigation follows academic laboratory conventions. The SHA-256 hash serves as an integrity verification mechanism; the investigation does not claim to satisfy legal chain-of-custody requirements applicable to court proceedings.

4.4 Phase C — Artifact Examination

4.4.1 Browser History Analysis

Autopsy's Recent Activity ingest module parsed the Chromium browser's SQLite History database located at C:\Users\John\AppData\Local\Google\Chrome\User Data\Default\History. The module converts Chromium's WebKit epoch timestamps (microseconds since 1601-01-01) to human-readable UTC timestamps. The browser history was examined under Results > Extracted Content > Web History.

Key findings from browser history (Findings F-004, F-006, F-007): A Google search for file compression techniques at 08:22 UTC, followed by navigation to wetransfer.com at 08:26 UTC, followed by a WeTransfer upload completion page at 08:28 UTC.

4.4.3 File System and MFT Analysis

The NTFS Master File Table (MFT) records timestamps for every file on the volume. Each MFT entry contains two sets of MAC (Modified, Accessed, Created) timestamps: the $STANDARD_INFORMATION attribute (user-modifiable, less reliable) and the $FILE_NAME attribute (kernel-controlled, more reliable for creation events). Autopsy displays both sets when a file is selected in the file system browser.

For this investigation, $FILE_NAME creation timestamps were prioritized for establishing when files were first created. The $STANDARD_INFORMATION access timestamp for company_data_Q3.xlsx was noted as supporting evidence with a medium confidence rating, acknowledging the potential for OS-level timestamp suppression.

4.4.4 Recycle Bin Forensics

Windows stores deleted-file metadata in C:\$Recycle.Bin\[SID]\. Each deleted file generates two records: a $I metadata file (containing original path, file size, and deletion timestamp) and a $R data file (containing the actual file content). When the Recycle Bin is emptied, the $R data file is removed, but the $I metadata file may remain recoverable in Autopsy's deleted file analysis.

In this investigation, Autopsy recovered the $I file for exfil.zip (Finding F-008), providing the original filename and deletion timestamp. The $R data file was absent, confirming that the Recycle Bin was subsequently emptied (Finding F-009).

4.5 Phase D — Timeline Reconstruction

Autopsy's built-in timeline tool (Tools > Make Timeline) generates a comprehensive chronological view of all file-system events, log entries, and extracted artifact timestamps. The timeline was filtered to the investigation date (13 September 2026) to isolate relevant events.

The raw timeline data was exported to CSV and processed using the project's normalize_timeline.py script, which normalizes timestamps to UTC, sorts events chronologically, removes duplicates, and produces the master timeline/incident_timeline.csv. 

python scripts/normalize_timeline.py \
    --input timeline/raw_autopsy_timeline.csv \
    --output timeline/incident_timeline.csv \
    --timezone UTC

4.6 Phase E — Artifact Correlation and Scripts

The artifact correlation map shows how the findings from different sources corroborate each other to form a coherent incident narrative. This is documented in analysis/investigation_notes.md and analysis/artifact_mapping.md.

The following Python scripts were developed and are included in the scripts/ directory:

  • hash_evidence.py — SHA-256 hashing for evidence integrity verification

4.7 Validation

All Python scripts were tested using the automated test suite in the tests/ directory. Tests use synthetic fixture data; no real evidence is required to run the tests. Key validations include:

6. Conclusion and Future Scope

6.1 Conclusion

The investigation directly answers the stated question: forensic artifacts on the suspect system do indicate unauthorized data access and exfiltration, and the reconstructed sequence of events is consistent with a deliberate insider threat incident.

The evidence shows that on 13 September 2026, user account 'John' logged on to the Windows system at 08:14:22 UTC, obtained administrative privileges, accessed a sensitive financial document (company_data_Q3.xlsx), searched for file compression techniques, created a compressed archive named exfil.zip, navigated to the WeTransfer public file-transfer service, completed what the browser history indicates was a file upload, deleted the archive and emptied the Recycle Bin, and then logged off — all within a 19-minute and 23-second session.

The anti-forensic attempt (deleting and emptying the Recycle Bin) was partially successful: the file content was irrecoverably deleted. However, the $I metadata file retained in the Recycle Bin directory disclosed the original filename, size, and deletion timestamp. Combined with the browser history and event log evidence, the overall incident narrative is well-supported.

6.2 Key Findings

  1. The suspect account had a focused, anomalously short session of under 20 minutes.
  2. Sensitive financial data was accessed at the start of the session.
  3. Browser history shows data staging (compression search) followed by upload to a public file-transfer service.
  4. Anti-forensic cleanup was attempted but only partially successful — Recycle Bin metadata survived.
  5. Nine of twelve findings carry high confidence ratings; no finding contradicts the insider exfiltration hypothesis.

6.3 Advantages of the Approach

  • Multi-source correlation: No single artifact proves the incident alone; corroboration across event logs, browser history, MFT, and Recycle Bin provides a robust finding.
  • Reproducibility: The investigation workflow is fully documented; the Python scripts are tested and deterministic.
  • Open-source tooling: Autopsy and TSK are freely available; the investigation is reproducible without commercial software.
  • Transparent limitations: Confidence ratings and explicit limitation statements for each finding prevent over-interpretation of the evidence.

6.4 Limitations

  • No network capture: The WeTransfer upload cannot be confirmed from local disk artifacts. Network packet capture or server-side logs would be required for confirmation.
  • Timestamp reliability: NTFS $STANDARD_INFORMATION access timestamps can be suppressed by the OS and should not be treated as conclusive.
  • USB evidence incomplete: The USB event (F-011) lacks user context and cannot be directly attributed to the 'John' account.
  • Educational dataset: All findings reflect a simulated scenario designed by TryHackMe; extrapolation to real-world incidents should be done carefully.
  • No behavioral baseline: The absence of historical logon patterns prevents quantitative behavioral anomaly analysis.

6.5 Future Scope

  • Integrating Wireshark or Zeek network captures would allow verification of the WeTransfer upload and determination of the transferred file size and recipient.
  • Volatility memory forensics on a memory dump captured at the time of the incident would reveal running processes, network connections, and any encryption keys in memory.
  • Behavioral baseline analysis using historical Security event logs would enable quantitative anomaly detection to identify unusual session durations or access patterns.
  • File carving on the unallocated space of the disk image could potentially recover the deleted exfil.zip content if the disk sectors have not been overwritten.
  • setupapi.dev.log analysis would reveal whether the USB device connected at 09:05 had been previously connected to the system and under which user account.
  • Applying MITRE ATT&CK framework mapping to the findings (Collection: T1560.001 Archive via Utility; Exfiltration: T1567 Exfiltration Over Web Service; Defense Evasion: T1070.004 File Deletion) would provide a structured threat intelligence output.

8.2 Key Script: hash_evidence.py

The following shows the core SHA-256 hashing function from hash_evidence.py: 

def compute_sha256(file_path: Path) -> str:
    """Compute the SHA-256 digest of a file without loading it fully into RAM."""
    if not file_path.is_file():
        raise FileNotFoundError(f"Not a file: {file_path}")

    hasher = hashlib.sha256()
    with open(file_path, "rb") as fh:
        while chunk := fh.read(65_536):   # 64 KiB buffer
            hasher.update(chunk)
    return hasher.hexdigest()

This function uses a streaming approach (64 KiB buffer) to handle large evidence files without loading the entire disk image into RAM.
